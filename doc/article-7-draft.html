If you've followed this series, you already know the cast: an M5Stack AtomS3, an Atomic Battery Base, and two toy drones that were never meant to talk to anything but their own apps. By Part 6 the story felt done — both drones reverse-engineered, both flying under our own firmware, the project basically "finished."

Then a question came up that the first six parts never had to answer: what happens if you point this firmware at completely different hardware?

Not as a hypothetical. While poking at Bluetooth controller support (more on that in a future part — there's a good story there), it became clear the AtomS3's chip simply can't do something a sibling board in the same product line can do. Before chasing that any further, there was a more basic question to settle: could this firmware even run on a second board at all, or was it quietly AtomS3-shaped in ways we hadn't noticed?

The rule: don't touch what already works

Six parts of careful engineering went into the AtomS3 build. It flies two drones reliably. The last thing this experiment was going to do was risk that for a "wouldn't it be nice" feature. So the constraint was simple going in:

The AtomS3 firmware has to come out the other side byte-for-byte identical — same RAM, same Flash, same behavior — or the second board isn't worth it.

This is exactly the kind of constraint the HAL pattern from Part 3 was built for, even though nobody was thinking about a second board back then. The whole point of BoardHal, DisplayHal, ImuHal, and ButtonHal was to keep every M5Unified call confined to one file. If that held up, adding a board should mean writing a second implementation of those structs, not touching the first one.

It held up. The AtomS3's m5atoms3.cpp didn't change at all.

What's actually different under the hood

The M5StickC Plus2 isn't just a different shell around the same chip. The AtomS3 runs an ESP32-S3; the StickC Plus2 runs an ESP32-PICO-V3-02 — the original ESP32 core, a different silicon family entirely. PlatformIO doesn't even have a dedicated board definition for this exact module yet, so the new environment borrows esp32-pico-devkitm-2 (the official Espressif devkit for the same chip) and lets M5Unified handle the actual pin mapping at runtime.

[env:m5stack-stickc-plus2]
platform = espressif32
board = esp32-pico-devkitm-2
framework = arduino
build_flags = -DBOARD_STICKC_PLUS2
build_src_filter = +<*> -<hal/m5atoms3.cpp>
board_build.partitions = huge_app.csv
upload_speed = 115200

Two of those lines exist because of problems the AtomS3 build never had to think about.

The default partition table on this board definition assumes a much smaller flash than the chip actually has, and our firmware — comfortably under the limit on the AtomS3 — didn't fit in either OTA slot. huge_app.csv trades the dual-OTA layout for a single, larger app partition. No OTA updates, but we weren't using them anyway.

The upload speed line is less elegant. The board flashed perfectly the first few times at the default 921600 baud, then started failing intermittently with serial noise right after the speed step-up — a USB-serial adapter quirk, not a code problem. Dropping to 115200 traded a few seconds of upload time for one that actually finishes.

Battery reading needed its own real rework, not just a recompile. The AtomS3's Atomic Battery Base has no I2C exposed at all — Part 1 covers the GPIO8/ADC2 voltage-divider approach we built to work around that. The StickC Plus2's battery IC is different hardware with a real I2C interface, and M5Unified already knows how to talk to it directly: M5.Power.getBatteryLevel(), M5.Power.isCharging(). The custom ADC sampling, hysteresis logic, and calibration table from Part 1 — all of it specific to working around the AtomS3 base's missing I2C — simply isn't needed here. Same BoardHal interface, completely different implementation underneath, exactly as the pattern promises.

// m5stickcplus2.cpp
const BoardHal kBoard {
    .begin           = [] { auto cfg = M5.config(); M5.begin(cfg); },
    .update          = [] { M5.update(); },
    .getBatteryLevel = [] { return (int)M5.Power.getBatteryLevel(); },
    .isCharging      = [] { return M5.Power.isCharging() == m5::Power_Class::is_charging; },
};

The display needed the least work, and that's the most satisfying part. The StickC Plus2's screen is a different size than the AtomS3's 128×128 square panel, so the HUD layout constants had to become conditional — but only the layout. The actual drawing code, the flight state machine, the drone protocols, the gamepad input handling: none of it knew or cared which board it was running on.

Confirmed on real hardware

Display, WiFi connection to the drone, and the iPega BLE gamepad all came up working on the first flash, no surprises. That's three of the AtomS3's four major subsystems transferring over essentially for free, which is about as strong an endorsement of the original HAL decision as this project is going to get.

(Tilt/accelerometer control is the one piece still unverified on this board — flagged honestly rather than claimed, since this team doesn't report things as "done" until they've actually watched them work.)

What this sets up

The reason this board mattered enough to write about wasn't "wouldn't it be nice to support more hardware." It's that the M5StickC Plus2's chip has a capability the AtomS3 fundamentally doesn't — and that capability turned out to matter a lot for a controller-support question this series hasn't resolved yet. That's the next story, and it's a good one: a feature closed out as flatly impossible, reopened by discovering the right hardware existed all along, just not in the box we'd already opened.
